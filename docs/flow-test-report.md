## 1. 測試方法

不讓搜尋引擎「自己驗自己」：每個流程的輸出都用 **QA 實際的使用方式** 重建盤面（貼上複製出來的腳本），再用另外撰寫的規則檢查器比對。

| 規則 | 內容 |
|------|------|
| R1 | 盤面上恰好一組「目標符號 × 連線數」中獎（同一組格子落在多條線只算一組），ways = 1 |
| R2 | 中獎位置上的百搭軸數 = 組合名稱的百搭數 |
| R3 | 除目標外沒有任何有贏分的中獎（含百搭自己成線） |
| S1 | 複製的腳本重建出的盤面 = 搜尋到的盤面（含 Way 遊戲的 Strip ID） |
| M1 | 羅馬：腳本第 2 行遞補後 0 贏分（雙重安全防線） |
| G1 | 金框掉落型（皇家金象 +WX）：初始盤面沒有目標中獎，金框消除轉 WX 後才形成目標連線 |
| F1 | 「複製全部測案」的 `Win=` = 依遊戲規則（掉落、倍數、不可消除符號）重算 |
| W1 / W2 | 大獎區間：搜尋引擎模型 / 測案 `Win=` 的倍率落在區間內 |
| C1 | COMBO：「N Combo」腳本重播後恰好連續消除 N 次（羅馬依滾輪表輪替 + 腳本遞補行重播） |
| L1–L3 | 贏分線路一覽：該線滿線中獎、其他線零干擾、羅馬附遞補且遞補後 0 贏分 |
| V1 / V2 | RNG 腳本驗證：貼入產生器腳本，工具算出的贏分 = 規則重算；羅馬用腳本第 2 行遞補 |
| 載入 | 測試腳本庫載入後的盤面 = 腳本盤面 |
| T1–T3 | 消除掉落測試：載入盤面、第一盤贏分正確，掉落後每格都是可辨識符號 |

全部使用固定亂數種子，結果可重現。已確認的問題以**精確筆數**鎖在 `knownIssues`：
出現新問題、問題變多、或問題被修好（筆數變少）都會讓 `npm test` 失敗並提示更新 —— 之後開發新遊戲若改壞任何流程會立刻發現。

## 4. 搜尋方式是否最優？

評估方式：每個「遊戲 × 符號 × 連線數 × 百搭數」用 3 個種子呼叫現行搜尋引擎，以第 1 章規則判定是否真的是乾淨解；引擎 3 次都失敗時，用 **依規則先篩選每軸停點的建構式取樣（oracle）** 證明是否存在解：
連線軸只挑「該格是目標 / 百搭」、Way 遊戲的連線軸只挑「視窗內恰好一個目標或百搭」、第 L+1 軸只挑「不含目標與百搭」。

| 遊戲 | 案例 | 引擎 3/3 乾淨 | 部分成功 | 3 次全失敗 | 其中 oracle 證明有解 | 引擎平均耗時 |
|------|----:|----:|----:|----:|----:|----:|
| 羅馬競技場 | 42 | 42 | 0 | 0 | — | < 1 ms |
| 皇家金象 | 64 | 64 | 0 | 0 | — | 262 ms（最長 733 ms） |
| 通用 Line Game | 48 | 35 | 13 | 0 | — | 36 ms |
| 人魚 / Way Game | 48 | ~~30~~ → **48** | ~~14~~ → 0 | ~~4~~ → 0 | — | 8 ms |
| 秦皇傳說 | 64 | ~~9~~ → **64** | ~~13~~ → 0 | ~~42~~ → 0 | — | 6 ms |
| 通用 Pay Anywhere | 32 | 0 | 0 | 32 | 0（要求的個數在此賠率規則下不可能中獎，見 F01） | 0 ms |

**結論：修正前不是最優；Way 類已修正（刪除線為修正前數字）。**

1. **漏解嚴重的是 Way 類**：秦皇引擎 3 次全失敗的 42 個案例，oracle **全部**找得到解，而且平均只要幾十次取樣；人魚 4/4 同樣如此。原因是引擎在 Way 遊戲只用「視窗內有目標」的停點隨機抽（60% 機率），沒有限制「恰好一個」、也沒有讓第 L+1 軸避開目標，命中 ways = 1 的機率極低，1000 次預算就耗盡。
2. **線遊戲成功率高但不穩定**：通用 Line 有 13/48 案例在部分種子下只拿到有干擾的解；引擎在 10% 的嘗試中不鎖定線路、純隨機，浪費預算。
3. **羅馬、皇家金象表現良好**：羅馬有專屬的純淨搜尋（< 1 ms、100%）；皇家金象 100% 但每次約 0.26 秒（3 萬次預算的隨機取樣）。
4. **贏分線路一覽的 DFS 很差**：依停點順序窮舉且上限 2500 次，前幾軸幾乎不變；羅馬 42 條「有干擾」中 34 條其實有零干擾解。

**建議的搜尋改法（不改變規則，只改找法）**：
- 預先為每一軸建立「停點分類表」：連線軸（恰一個目標 / 恰一個百搭）、第 L+1 軸（無目標無百搭）、其他軸（任意），只在合格停點中取樣 —— 即 oracle 的做法，秦皇失敗案例平均數十次即命中。
- 取樣失敗後改為**決定性窮舉**合格停點的乘積（每軸合格停點通常只有數個到數十個），讓「找不到」= 真的不存在，而不是預算用完。
- 贏分線路一覽改用同樣的分類取樣，取代依序 DFS。
- 秦皇 +WX：滾輪表沒有金框時改走一般百搭搜尋（WX 直接出現在盤面）。
